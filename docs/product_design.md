# 产品设计

## 1. 一句话

为订单主系统提供一个**可独立启动的 gRPC 订单查询演示服务**，用于学习与验证「查询侧」微服务拆分，而不是替代完整交易系统。

## 2. 目标用户 / 使用场景

| 角色 | 场景 |
|------|------|
| 学习者 / 面试演示 | 展示 gRPC + protobuf + 分层架构 |
| 开发者本地联调 | 用 grpcurl / HTTP 按订单 ID 读主库数据 |
| 后续拆分参考 | 为真正的 order-query 服务留接口与分层样板 |

## 3. 问题与价值

| 问题 | 本项目如何回应 |
|------|----------------|
| 主系统只有 HTTP，想练 gRPC | 独立进程暴露 `OrderService` |
| 直接改主系统成本高 | 旁路项目，共享读库，不侵入主仓库业务 |
| 需要快速验证「能否查到订单」 | 双入口：gRPC + 简单 HTTP |

## 4. 范围

### 4.1 In Scope（当前）

- 按订单主键查询
- 与主系统订单表字段对齐（读模型）
- gRPC 与 HTTP 两条只读通路
- 文档：目标、架构、API、测试、迭代

### 4.2 Out of Scope（当前明确不做）

- 完整下单、扣减库存、Redis 预扣
- 幂等键、超时关单、支付回调
- JWT / RBAC 与主系统一致的鉴权
- 管理后台、商品管理
- 独立订单库与数据双写

## 5. 核心用户故事

1. **作为**开发者，**我希望**启动本服务后用 gRPC 按 `order_id` 查到主库订单金额与基础信息，**以便**验证查询链路。
2. **作为**开发者，**我希望**同时有一个 HTTP GET，**以便**不装 grpcurl 时也能快速看数据。
3. **作为**维护者，**我希望**文档写清与主系统边界，**以免**误把写逻辑做进本服务。

## 6. 成功标准（MVP）

- [x] 配置正确时进程可启动并连接主库
- [x] `GetOrder` gRPC 可对存在的订单返回结果
- [x] `GET /api/v1/orders/:id` 可返回订单 JSON
- [x] README / 架构 / API / 测试文档可指导他人复现
- [ ] gRPC 响应字段与错误码达到可对外约定的完整度（进行中）

## 7. 体验原则

1. **查询优先**：先保证读路径清晰、可演示
2. **边界清晰**：写路径引导回主系统
3. **契约显式**：proto + docs 说明字段与已知限制
4. **可本地复现**：配置、端口、grpcurl 示例写在 README

## 8. 风险与对策

| 风险 | 对策 |
|------|------|
| 直连库绕过主系统鉴权 | 文档标明仅演示；后续可改只读 API |
| 误用 CreateOrder 写脏数据 | 文档标占位；演进中可返回 Unimplemented |
| proto 与实现字段不一致 | 在 API 文档标注「当前实现」与「契约目标」 |
| 与主系统表结构漂移 | 模型与主系统对齐；变更跟主库 migration |

## 9. 演进路线（产品视角）

| 阶段 | 产品形态 |
|------|----------|
| 现在 | 旁路查询 demo |
| 下一步 | 查询响应完善 + 列表 + 标准错误 |
| 可选 | 只读 API 网关，不再直连 DB |
| 远期 | 若业务需要，再评估独立 order-query 服务与事件同步 |
